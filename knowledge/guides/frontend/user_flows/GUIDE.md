# User flows (of_test.js)

When the owner turned user-flow tests on (an experimental setting, off by default; `project_state` says when they are off: then write none), a project with pages or an API ships `of_test.js`: what a real person (or client) does with THIS project,
saved with `manage_testing action=write_flows`, which replays it at once; the post-build
validation replays it again. It is plain data - `export default { flows: [{ name, viewport?, steps: [...] }] }`,
no imports or functions, one verb per step. Keep it small: at most 5 flows (one per core
journey, plus a phone flow when people use the project on phones), about 12 steps each.
**Recall the `writing-flows` section below right before you write or re-save it** - it carries
the exact step verbs, how selectors and extra users work, what to cover for each kind of
project, and what to do when a flow is red. A red flow is an app bug (fix the code) or a script
that drifted from the UI (re-save it). Never weaken an expectation to hide a real bug, and
never change security, sign-in or access settings, platform configuration or intended
behavior to make a flow pass: a flow that conflicts with the brief or the platform is the
wrong one, so fix the flow.

## Writing flows
> when: you are about to write or re-save of_test.js (the user-flows checklist item, or a change that renames, moves or removes something a flow uses).

**Read before you write.** Open every page and script a flow will drive (`manage_files get` or `outline`) and copy selectors and visible labels verbatim. Never guess a class, a `data-` attribute or a piece of copy: most flows that go red on their first replay fail on a name the script made up. Assert text only if you read it in a file or saw it in seeded data. The save result lists selectors and labels it finds in no project file.

**A save replaces the whole file.** When you add a feature, start from the saved script (`manage_files get of_test.js`), keep every flow whose feature still exists and add the new ones; the suite may pass 5 flows, a working flow is never dropped to stay under it. A save that leaves out a saved flow is refused (the refusal carries the saved script); list a flow in `drop` only to delete it on purpose.

**Act:** `{goto:"/path"}` `{reload:true}` `{leave:true, as:"bob"}` (that user closes their tab; a later `goto` as the same name opens a new, blank browser) `{click:sel, at?:[x,y]}` `{dblclick:sel}` `{hover:sel}` `{drag:sel, to:sel}` or `{drag:sel, path:[[x,y],...]}` `{fill:sel, value}` `{type:sel, value}` (key by key, for code boxes and search-as-you-type) `{select:sel, value}` `{check:sel}` `{uncheck:sel}` `{press:"ArrowLeft"|"Enter"|"Space"|char|"Shift"|"Shift+Enter", hold?:ms}` ("Shift+w" with hold holds both) `{upload:sel, value:"image.png"|"photo.jpg"|"notes.txt"|"data.csv"|"data.json"}` (sel: a drag-and-drop UI's drop zone, else the file input or its label) `{download:sel, value?:"part of the file name"}` (click and wait for the file) `{scroll:sel|"bottom"|"top"}` `{wait:ms}` `{remember:"name", from:sel, attr?:"href"}` (store a value the app generated - share link, room code, order number - as `{{name}}` for every later step, session and flow, e.g. `{goto:"{{name}}", as:"bob"}`; the value is stored as read, and goto or request uses only the path of a full URL) `{dialog:"accept"|"dismiss", value?}` (how to answer the NEXT alert/confirm/prompt; default accept) `{offline:true|false}` `{clock:"+1d"|"-2h"|"2030-01-15T09:00"}` (moves the page's clock; server time stays real).

**Assert:** `{waitFor:sel}` `{expectVisible:sel}` `{expectHidden:sel}` `{expectText:"..."}` `{expectNoText:"..."}` `{expectUrl:"/path"|"/path#hash"|"/prefix*"}` `{expectCount:sel, count}` `{snapshot:sel}` then `{expectChanged:sel}` (its pixels changed) `{expectAnimating:true}` (render loop running) `{expectJs:"<expression>"}` (ONE expression on app state, polled until truthy; a promise is awaited).

**Beyond the page:** `{request:"POST /api/orders", body?:{...}, headers?, status?}` (sent from the session's tab with its cookies and signed-in token; any 2xx unless status says otherwise) then `{expectResponse:{...}|"text"}` (JSON subset, or text in the body) and `{remember:"id", from:"response.id"}` (a path like `response.items.0.id`). `{expectEmail:"text", to?}`: what the app sent - kept, never delivered, during a replay - to the session's `{{email}}` unless `to` names another recipient; then `{remember:"link", from:"email.link"}` (or `email.code`, `email.body`). `{runSchedule:"name"}` runs a native_action scheduled task now. `{webhook:"name", body}` POSTs a correctly signed body to the inbound webhook. A flow-level `users:{admin:{role:"admin", signedIn?:true}}` creates accounts before it starts: log in as `{{email:admin}}`/`{{password:admin}}` (steps `as:"admin"`), or start already signed in - for roles a signup cannot give and apps whose only login is an outside provider. Checkout: during a replay the payments tool opens the platform's test checkout - click `#of-checkout-pay` (or `#of-checkout-cancel`) and expect the paid state.

**Every step** takes `timeout` (ms, default 5000 - 20000 for expectEmail, 15000 for request/webhook, 45000 for runSchedule - max 60000) and `as:"<name>"` (run it as another user, in their own browser). Text checks, clicks, fills and element checks take `in:sel`: act or look only inside the elements matching sel (a row, card or column); a selector may use `:has-text("...")` (its text contains ...; CSS in steps only, not in expectJs), so `{click:"text=Delete", in:".row:has-text('Order {{run}}')"}` or `{click:".row:has-text('Order {{run}}') .delete"}` deletes YOUR row. at/path points are fractions of the element box (0..1). sel = CSS (give every targeted control or canvas an `#id`) or `text=<exact visible label>`; both reach into web components. viewport: desktop (default) | tablet | mobile | mobile-landscape | tablet-landscape (touch: clicks are taps, drags are swipes; phone UA). `{{email}}` `{{password}}` `{{username}}` `{{phone}}` differ per session (`{{username:bob}}` reads bob's); `{{run}}` is ONE 8-character value for the whole replay, the same in every session and flow - mind a field's maxlength. `{{totp:secret}}` is the current 2FA code for a secret an earlier step remembered.

**Data.** Each flow and each session starts as a brand-new visitor: logged out, no cookies, localStorage or IndexedDB - nothing an earlier flow saved in its browser, so keep steps that depend on it in one flow. Server data is different: records earlier flows created are still there until the replay ends (then every change is rolled back). So create the records a flow works on (name them with `{{run}}`) and act on them by that name with `in:`, never by position (`:last-of-type`, the first Start button) or by the state of existing rows - real users change those on a live app.

**What fails a step:** a timeout, a failed assertion, or ANY JS error it triggers in any session. The test browser has a fake camera and microphone, grants clipboard, location (central Amsterdam) and notifications, and runs WebRTC, service workers and WebGL; only an install prompt and real push delivery are missing, and audio, reading a QR code from the fake camera and pointer-lock mouse look cannot be checked at all - leave those out of the flows, never change the app for them. Never replace of_test.js with diagnostic flows: a red report already lists what the page showed where the step looked, JS errors, failed requests and scripts, and the visible controls. Flows re-run on later days: never assert date, clock or random text (a month name, a timestamp) - assert structure, or set `clock` first. Async results (an LLM reply, a save, a search) show their container at once with a spinner inside: never just `waitFor` the container - wait for the FINISHED state (`expectHidden` on the spinner, then `expectJs`/`expectText` that the result is non-empty and not the app's error), or a failed request passes as green. During a replay the app's own model calls (LLM and agent endpoints, `ctx.llm`, llm_call triggers and jobs) are answered instantly by a stand-in that replies "Test reply from the replay model." (or, for an endpoint with a response schema, sample JSON of that shape): assert that a reply appears, the loader goes away and the result is saved or shown, never what the model said, and keep the default timeouts. Other third-party services are real, so a flow that depends on one should check only that the app copes with its answer.

**A flow must prove what its name says.** `write_flows` returns `warnings` for a flow named for several people that never acts as a second user, an interaction flow with no acting step, and assertions that hold for any state, read a test-only global or read browser storage; the replay adds `weak_checks` for steps that passed without showing much. Fix them on your next save.

**Cover what a user does in THIS project, asserting on what they would notice.** Pick the bullets that match this project's shape (site, app, headless API, game, real-time) and skip the rest: the journeys a person would complain about first, not every feature. A second user only where the project is about two people. For anything real-time, assert the connection and the UI states a person sees (joined, connected, message shown), not media quality.
- DOM app - sign up, log in, create/edit/delete each kind of data (put `{{run}}` in titles, delete what you create); a second user must not see the first one's private data.
- Sign-in extras - a confirmation or magic link (`expectEmail`, `remember from:"email.link"`, `goto` it), 2FA (`{{totp:secret}}`), an admin or other role (`users`).
- Headless API - request chains per resource (create, read back, update, delete), sign up/log in, and a refused request (bad input, no permission) with its `status`.
- Site - visit every page via its nav links and expect its heading; submit its forms and `expectEmail` the notification they send (`to` the owner's address).
- Canvas/WebGL game or 3D scene - start it, `expectAnimating`, drive it with press/hold/click at (taps on a phone), then assert the effect on the HUD the game already shows (score, coins, position, a status line) with `expectText`/`expectJs` on that DOM. `expectChanged` on the canvas alone proves nothing when the scene animates by itself: the replay says so in `weak_checks`.
- Drawing/editor/map - drag a path or click at points, `expectChanged`. Boards/lists - drag `to`. Uploads - upload then expect the result. Exports and files - `download`.
- Chat/multiplayer/collaboration - act as main and as `"bob"` and expect each to see the other's action, then `leave` as one of them and expect the other to see them gone (presence list, a "left" message). A flow named for two players must act as two. Video/voice calls - both join, then `expectJs` that the remote video's `videoWidth > 0`.
- Anything that updates live (boards, feeds, dashboards) - keep it open in one session and act in another, with NO goto/reload in the watching session before its expect.
- Anything that generates a link or code (share, invite, order, room) - `remember` it and open it, often as another user, to test the far end.
- Installable/offline app (PWA) - load it, `offline:true`, `reload`, expect it still works; streaks and day-based views - `clock:"+1d"`.
- Automation - `runSchedule` or `webhook`, then check the effect (`request` + `expectResponse`, `expectEmail`). Payments - pick a plan, pay on the test checkout, expect the paid state.
- Destructive actions - `dialog:"dismiss"` keeps the item, confirming removes it.
- Mobile-first - a `viewport:"mobile"` flow.

Re-save whenever a change renames, moves or removes something a flow uses.

**When a flow is red.** The failure names the step, the page, the JS errors, the failed requests and the controls on screen: read it before touching anything.
1. Decide whether the app is wrong (fix the code) or the script is (re-save that flow).
2. A click that fails because another element covers its target is an app bug: a real user cannot click it either. A layer meant to be hidden must really be hidden (`[hidden]` loses to a `display:flex` rule, so add `[hidden]{display:none}` or toggle a class), and a decorative layer needs `pointer-events:none`.
3. Never change security, sign-in or access settings, platform configuration, endpoint gating or intended behavior to turn a flow green. If the flow expects something the brief or the platform does not allow, the flow is wrong: fix it in place.
4. Never replace `of_test.js` with diagnostic flows; once replays stop getting closer to green, a save that drops most of the saved flows is refused. Investigate with the code and the report: it ends with the page's console output. A replay rolls back every row it created when it ends, so a record a failing step acted on no longer exists afterward: probing it with `test_endpoint` (e.g. `PUT /api/messages/1`) 404s and proves nothing, so read the page and endpoint code instead. To see inside a silent failure (a step that never completes), add a `console.log` at the suspect line and replay that one flow (`manage_testing action=test_flows` with `flow`), not a diagnostic module; remove the logs when done.
   Never add test-only globals, hooks or debug exports to the app (`window.__x = ...`) for a step to read: assert on what a person sees (text, visibility, counts, the URL), or on state the app already exposes for its own use.
5. Every save replays, so save once per fix. Each result shows the replays left and the replays in a row without progress (a replay that fails further into its steps counts as progress). Fix a red flow now when you know the cause: the post-build repair pass is short. After 3 replays in a row that get no closer to green, stop and complete the item: the post-build validation replays the flows once more and reports any still red to the owner as a check that did not pass.
